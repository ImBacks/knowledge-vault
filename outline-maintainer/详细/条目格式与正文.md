# 条目格式与正文（outline-maintainer 详细模块）

> **何时读：收录任何条目动笔前（SKILL.md 任务分发表的硬指针）。**
> 内容 = 原 §3 条目格式细则 + §13 示例 + §15 知识正文 + §16 留证不留档 + `大纲.md` 骨架。
> 主流程（闸门 / 去重 / 落盘清单）在 `收录.md` §4，来源在 `收录.md` §8，禁令在 `收录.md` §14；落盘走 `写入协议.md` §7。均不在此重复。

# 3. 条目格式

两类条目，格式不同。**判断依据是"以后怎么用它"**：直接拿来用 → A；需要读懂、内容长 → B。

## A. 工具条目（短，单行）

```
- **名字** ｜ 作用：短语 / 短语 — 一句说明 ｜ 形态：工具 ｜ 限制：（可选） ｜ 来源：github.com/x/y ｜ 活 2026-10-23
  - 备注：（可选，一行，不计入条目数）
  - 用法：（可选，YYYY-MM-DD 一句话，用过再补，不计入条目数）
```

- **作用 ≤ 60 字**，按「短语 / 短语 — 说明」写（见下）。
- **不建正文文件**。
- **不写平台 / 生态的枚举，不写依赖清单。** 那些在 README 里随时能查，写进索引只是噪音，而且会过期没人改。**只有构成硬限制时才用 `限制：` 写一句**（见下）。

## B. 知识条目（长，索引行 + 外置正文）

```
- **名字** ｜ 作用：短语 / 短语 — 一句说明 ｜ 形态：文章 ｜ 来源：B站@某UP「标题」12:34 ｜ 正文：知识/信息管理/名字.md ｜ 活 2026-10-23
  - 备注：（可选）
```

- **作用 ≤ 60 字**，同样只写检索锚点，不承担"讲清楚"的职责。展开内容全部进正文。
- **必须带 `正文：` 字段**，值为相对库根目录的路径，用 `/` 分隔，带 `.md`。
- **路径规则**：`知识/<子类名>/<名字>.md`，子类名与 `###` 标题逐字一致；文件名与条目名一致，名字里出现 `\ / : * ? " < > |` 时替换为 `-`。
- **重名加限定**（`名字（作者/平台）`）时，文件名用限定后的全名。
- 正文怎么写见 §15。**正文字数不设上限**。
- 一份长材料（一本书 / 一份大 PDF / 一个长视频）默认 = **1 条知识条目 + 1 个正文文件**，章节在正文里做二级标题，不要每章建一条。

## 两类共用规则

- **作用字段必须写成可切分的形式**（为将来的机械索引留路，现在零成本）：
  ```
  作用：视频下载 / 去水印 / 批量导出 — 支持 B站、YouTube，可断点续传
  ```
  - `/` 前面是 **2–6 字的名词性功能短语**，就是将来要检索的那个词；`—` 后面才是补充说明。
  - 现在靠 LLM 读，这样写照样能懂；条目过千要上倒排索引时，直接按 ` / ` 切开就是标签，**不用回头改全库数据**。这是唯一一件"现在不做、以后要动全部条目"的准备。
  - **不要把短语切成单词**（「修改」「视频」「工具」这种），切太碎会大量误命中——切分粒度就是检索粒度。
  - 短语总数控制在 3–5 个。超过 5 个说明这条其实是多个工具，该拆条。

- **分隔符固定 ` ｜ `（左右各一空格）**。字段内部要出现这个序列时，改写为 `／`。
- **名字是主键，必须唯一**。重名加限定：`**名字（作者/平台）**`。
- **形态**：`工具｜网站｜插件｜Skill｜项目｜模型｜课程｜书｜文章｜概念｜硬件｜服务`。主形态必填一个；次形态写在括号里，最多一个，如 `形态：网站（Skill）`。
- **形态判定（不猜，看实物）**：怎么用就写什么——独立运行的 CLI / 软件 / 网站 → `工具` / `网站`；装进 AI 助手才能用的技能、插件（仓库有 `SKILL.md`、`skills/`、`.claude-plugin` 等标志）→ `Skill` / `插件`；两者都支持时，主形态按主要使用方式写，另一个进括号。**有仓库 / 官网的，先看 README 和目录结构再定形态，不默认写工具；确实查不到才按口播描述定并标 `（待核验）`。**
- **限制（可选，只在有硬限制时写一句）**：`限制：仅 Windows` ｜ `限制：macOS 仅重链接` ｜ `限制：需自备游戏文件` ｜ `限制：AGPLv3 商用需评估`
  - **只记「例外」，不记「支持」**。全平台可用就整个字段省略——写 `平台=Windows,macOS,Linux` 的信息量是零，因为绝大多数工具都这样。
  - 判断标准只有一句：**这条限制会不会让人装完才发现不能用？** 会，就写；不会（比如某个次要功能是实验性的），就别写。
  - 旧的 `范围：平台=…;生态=…;领域=…` 已废弃。见到就改成 `限制：` 一句话，或直接删掉。
- **来源**：见 §8。
- **活（必填，格式 `YYYY-MM-DD`，不带冒号，前面一个空格）**：该条目的**最近活跃日期**，只有一个，刷新式更新。
  - **三个刷新时机**：① 写入（新建或实质修改）② 检索时被命中 ③ 后续材料又提到这个条目（复现）。
  - 语义是「最近一次被碰到」，**不是「最近一次被采用」**。用户就是这么定义的，照做，不要自作聪明改成只记采用。
  - 用途：看活跃状态，判断这条还值不值得留。**删不删由用户提，不要主动建议淘汰。**
  - 每次刷新都要顺手核对：日期是当天、格式 `YYYY-MM-DD`、不是未来日期。
- **核（可选，格式 `核 YYYY-MM-DD`，写在 `活` 之后）**：最近一次**联网核验通过**的日期。
  - **只在真正访问一手地址、核实过事实时写或刷新**（§0 的"核验"）；检索命中、只改格式、离线修正、批量迁移都不动它。核验没通过（查不到新地址）不写。
  - `活` 回答「这条最近被用过吗」，`核` 回答「这条的事实多久前核对过」。两个日期语义不同，**永不打散合并**。
- **别名（可选，`别名：词；词`，`；` 分隔）**：同一东西的其它叫法——用户检索用过的词、常见改写、旧名（§6 改名）、UP 主的念法。任一别名即可命中。
  - 写入时机：① 检索命中后按 §5 末条提议补写；② 改名 / 合并时旧名落这里；③ 用户随口给了叫法当场记。
  - 别名是检索数据，不进备注；不算作用短语，不占「短语 3–5 个」的名额。
- **没有独立的状态字段**。三种情况直接写在作用末尾：`（待补充）` 信息不全 ｜ `（待核验）` 没验证过 ｜ `（已失效 2026-10）` 确认坏了。
- **备注**：**一行，只写两件事，不设字数上限**——① 来源出处（格式同 §8，每次完整写，**禁止「同上 / 同视频」指代**）② 一句「口播 vs 一手材料」的差异（如「口播称 21 个技能，实为 7」）。出处完整比字数重要。
  - **不写**：安装步骤、依赖版本、功能清单、优缺点、评价。要么在 README 里，要么不该进索引。
- **用法子行（可选，两类条目通用；知识条目也可写在正文「我的用法」节）**：`  - 用法：2026-12-03 一句话`，**只追加，每行带日期**，不计入条目数。
  - **只在真用过 / 试过 / 踩过坑时写。** 用户的入库主场景是顺手收藏（"将来或许有用"），此时**默认不写、不问、不催**。
  - 收录时用户顺口给了具体契机（"因为最近在做 X"）→ 记一行；只说"或许有用"就不记。
  - 价值：将来一次检索命中多条时，"用过的是哪个、好不好用"只能来自这里（§5 输出对有用法记录的条目标 ✱）。
- **未知先查，查不到才写 `?`**。`?` 是「核验过、确实查不到」的标记，**不是省事的默认值**。
- **一手材料优先（硬规则）**：视频 / 截图 / 口播只是**线索**，不是事实来源。落盘前必须做完这五步——
  1. 按名字找到一手地址（GitHub / 官网 / npm / PyPI）。名字可能被念错，多试几个变体。
  2. 读 README 的 What it does / Features / Requirements，再用目录结构判断形态。
  3. **用一手材料重写「作用」，不要翻译口播。** 口播说「支持 15 种格式」就去数，数不出来就把这个数字删掉。
  4. **分类也按一手材料定**：README 说它是干什么的，就归哪一类，不照抄视频作者的归类。
  5. 口播与一手不一致 → **以一手为准**，备注记一句差异。
  - 找不到一手地址时：作用写成视频原话并标 `（待核验）`，**不得当成事实**。
  - **只核验本次写入 / 更新的条目**，不重查库里已有的其它条目（§0 校验≠核验）。
- **依赖和平台不查也不写**。用户不需要在索引里知道「需 Node 22+」——那是装的时候才会遇到的问题，README 里写着。写了只会在半年后变成过期信息。
- **口播数字必须核对**：视频里说的「内置 21 个技能」「59 条规则」这类具体数字，一律以 README / 代码为准；对不上按 README 写，并在备注注明「口播为 N，README 为 M」。

# 15. 知识正文

## 位置与命名

`<库根>/知识/<子类名>/<名字>.md`。子类名与 `###` 标题逐字一致。

## 头部（强制）

```markdown
# 名字
<!-- 正文：v0 ｜ 字 0 ｜ 提取 2026-10-23 ｜ 来源 本地:原文件名.pdf -->

（正文）

## 出处
- 来源：本地:原文件名.pdf（未在库内留档；原件在用户本机）
- 提取：2026-10-23，多模态解析（模型 ?）
- 引用：
  > 原句一（P.12）
  > 原句二（P.47）
- 原文未明说、由我推断的部分：…
```

- 第 1 行必须是一级标题，与条目名一致（脚本会校验）。
- 第 2 行必须是 `<!-- 正文：… -->`，含版本、字数、提取日期、来源。**这份材料要是复制进了 `素材/`，写 `素材/文件名`；没留档就写 `本地:原文件名`**，不许留空。
- 每次改正文，更新 `字 N`。

## 骨架（建议，不强制）

字数不是问题，**结构才是**。检索时你要能判断"这段要不要读"，靠的就是分段：

```markdown
## 摘要          <!-- 超过 1500 字必须有，5 行以内，供检索时判断要不要读全文 -->
## 说了什么       <!-- 原文的核心主张，按原文顺序 -->
## 关键结论       <!-- 可直接用的结论，标页码/时间点 -->
## 方法论         <!-- 可选：课程/长会话/长访谈等方法论密集材料收录时提炼——剥掉案例剩流程，步骤化可复用；由我提炼标「（推断）」 -->
## 边界与前提     <!-- 原文自己说的适用范围、样本、反例 -->
## 我的用法       <!-- 可选，标「非原文」。顺手收藏的默认空；真用过再补，每条带日期 -->
## 出处
```

## 硬规则

1. **不设字数上限。** 但超过 **1500 字**的，必须加 `## 摘要`（5 行以内）——否则命中后无法快速判断要不要读全文，等于没有检索价值。
2. **推断标记**：`（推断）`。跨页拼接、由上下文补全、由常识补齐的，都算推断。
3. **逐字引用**用 `>` 引用块，并标页码 / 时间点：`> …原文… （P.42）`。
4. **原文没说的不往里写**。要补充就单开 `## 补充（非原文）`，与原文明确分开。
5. **一份材料一个文件**。同一主题的第二份材料，追加到 `## 补充`，并在头部记第二个原文路径；不要新建重复条目。
6. **矛盾对照**：`## 补充` 的内容与原文既有结论冲突时，**在正文顶部并列两说、各自带出处与日期**（「说法 A（来源，2026-10）：… ／ 说法 B（来源，2026-11）：…」），不悄悄覆盖、不替原文改口。哪边对由后续核验裁决，裁决前两说并存。
7. **聚合页（L2，触发式，不预先造）**：同一主题被反复检索命中（近 30 天同主题检索命中 ≥3 次，或单次命中 ≥5 条——数据源是 §17 检索行）时，为该主题建一篇聚合页：它是**知识条目的一种**，照常算条目数、有索引行与 `正文：` 路径（建议命名 `知识/<子类>/_主题综述.md`，`_` 前缀示意"汇编"）、`活` 照刷、体检照查。来源写 `汇编自：[[条目A]]、[[条目B]]、…`；内容是跨条目的工作流与组合建议，标 `（汇编，非原文）`，引用成员条目用 `[[双链]]`。触发由检索时 agent 顺手判断并提议，用户点头才建——检索不主动建页。

# 16. 原文留存：留证，不留档

## 默认规则：不复制原文件

**默认不把 PDF / 图片 / 视频复制进库目录。** 体积撑不住：PDF 平均 2–5MB，1000 份就是 2–5GB；视频是 GB 级。存几百条之后，库比资料本身还占地方，而**你几乎不会回头重读整份 PDF**。

替代方案是**留证**：在正文里保留你真正依赖的那几句原文 + 页码/时间点。三行引用比三兆 PDF 有用——因为引用是结论的依据，整份 PDF 只是背景。

```markdown
## 出处
- 来源：本地:某报告.pdf（未在库内留档，原件在用户本机）
- 提取：2026-10-23，多模态解析（模型 ?）
- 引用：
  > 原句一（P.12）
  > 原句二（P.47）
```

条目侧只写 `来源：本地:<原文件名>`。原文件名不丢，用户自己能找到。

## 只有这三种情况才复制进 `素材/`

1. **孤本**：网上找不到、用户也只有这一份（扫描件、绝版资料、自己录的）。
2. 用户明确说「留一份」。
3. 单文件 < 5MB 且是整条结论的唯一依据。

复制时命名 `<条目名>__<原文件名>`，`素材/` 必须进 `.gitignore`。

## 但要承认代价

不留原件，就无法在半年后回头核对「当时 AI 是不是看错了」。所以留证要做扎实：

- 引用必须**逐字**，不许改写后当引用；
- 页码 / 时间点必须有；
- 表格和数字类结论，宁可写「跨页未核清」也不要留一个孤零零的数字。

**这是明确的取舍：用"引用可核"换"原件全存"。** 如果某份材料重要到你愿意为它花 5MB，就走上面第 1、2 条。

体积账（让用户自己判断）：1000 份 PDF ≈ 2–5GB；100 个视频 ≈ 50–200GB。这个量级不放在云同步目录里。

## 附：`大纲.md` 骨架（新建库时的样板）

**`大纲.md` 骨架**（干净到只有两块：目录 + 条目）

```markdown
<!-- v1 ｜ 条目 0 ｜ 更新 2026-10-23 -->
# 大纲

## 目录
- 工具库 › 视频 › 视频下载（7）
- 知识库 › 信息管理 › 收集方法（1）

## 工具库
### 视频 › 视频下载
- **SaveTube** ｜ 作用：视频下载 / 去水印 / 批量导出 — 支持 B站、YouTube ｜ 形态：工具 ｜ 来源：github.com/x/y ｜ 活 2026-10-23
  - 备注：B站@某UP「10个插件」03:12

## 知识库
### 信息管理 › 收集方法
```
