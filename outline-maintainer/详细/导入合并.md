# 导入与合并（outline-maintainer 详细模块）

> **何时读：用户给到别人的大纲要并入时。** 脚本用法见 SKILL.md 内置脚本节；落盘一律走 §7 写入协议。

# 20. 导入与合并（单向）

开源后有人把**他们的库**给你（反之亦然），需求是「把对方的库并进我的库」。定调：

- **只做单向导入：本库是主，对方只读。** 不做双向同步，不做「完整自动合并」——分类树是个人化的（对方的 `视频 › 下载工具` = 你的 `视频 › 视频下载`），作用短语是各人按自己的检索语汇写的，机器对不齐。能机械化的只有匹配与分诊（脚本），判断归 agent，裁决归用户。
- **禁止对 `大纲.md` 做文本级 git merge。** 两库插入位置不同，文本冲突不可收拾。合并只发生在条目级。

## 流程

1. 用户给出对方 `大纲.md` 路径（或库根目录）。跑 `merge_outline.py <本库大纲.md> <对方大纲.md>`（只读），得到四类分诊：

   | 类 | 判定 | 处置 |
   |---|---|---|
   | A 直接并入 | 归一化名字、来源 URL 都无冲突 | 按本库分类树归位：同名子类直接归；缺子类就新建、挂主题最近的大类；连大类都缺才新建（§1 相邻原则）。作用短语按本库语汇复写 |
   | B 同名同物 | 归一化名字相同、来源不矛盾 | 合并：`活`/`核` 取较新、`别名` 取并集、对方 `用法` 行追加；`作用`/`形态`/`限制`/`来源` 以本库为准，对方写法有增量信息（更准的形态、更全的来源）由 agent 对照后改 |
   | C 疑似同物 | 名字不同、来源 URL 相同 | agent 仲裁名字与描述（同 §4 疑似重复规则），列候选让用户选保留哪个名字 |
   | D 同名需仲裁 | 归一化名字相同但来源互斥 | 大概率同名不同物：agent 读双方来源与作用判断，用户裁决（两个都留 / 加限定改名 / 放弃导入） |

2. agent 对 B/C/D 逐条仲裁。联网核验**只核本次导入涉及的条目**（§0 铁律不变），不连带查兄弟条目。
3. 生成落盘清单（§4 格式），**等用户确认**。
4. 落盘走 §7 写入协议（含第 10 条写锁）。知识条目两处写入：对方正文文件**复制**成本库正文（按归位后的子类路径）；目标已有同名正文时按 §15 追加 `## 补充`，不覆盖。
5. 操作日志追加一行，动作写「导入」，备注写来源库与各类条数（如「来自 @user：A 12 B 2 C 1 D 1」）。

## 字段策略

- **客观字段导入**：作用（必要时按一手材料重写）/ 形态 / 限制 / 来源 / 别名 / `活` / `核`。
- **个人字段不自动导入**：对方备注先看内容——「口播 vs 一手」这类客观差异可并，主观评价不并；本库已有备注时以本库为主。对方的「我的用法」正文节不导入。
- **导入不等于核验**：对方的 `核` 日期可以采纳（对方核过就是核过），`（待核验）` 标记照带，不因换了库就当核过。
- **`- 相关：` 悬空**：导入条目的相关指向既不在本库也不在本次导入集 → 脚本会列出；要么连带导入该条，要么修剪该行，不留悬空（体检硬错误）。
- 每条导入条目按 §3 格式过一遍再落盘；对方库自身的坏格式（缺 `活`、缺来源）在导入时修正，不原样搬运。
